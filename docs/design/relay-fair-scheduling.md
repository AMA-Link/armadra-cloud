# 同一隧道的写端公平调度（#57）

> 状态：Go 中继已实现；core 侧（Armadra 仓）与 Workers 中继未改，见 §6、§7。
> 关联：AMA-Link/armadra-cloud#57、`go-relay-design.md` §3.3。

## 1. 问题与现状

一个源的全部流共用一条隧道（一条 WebSocket、8 MiB 隧道窗口、每流 256 KiB 窗口）。写端若按到达顺序出帧，一条流在传大文件时，同一台主机上别的流（终端按键与回显）要排在它已经发出去的字节后面。

Go 中继在 G1 就做了「每流每轮一帧」的轮转（`Tunnel.collect`），所以已经不是纯先进先出，但还有三处会让交互流多等：

1. 每批取走「全部控制帧 + 每个就绪流一帧」再串行写。批里有 N 条就绪流时，批中途到的 PONG、WINDOW 与交互流的第一帧要等整批写完，再在下一批里排到 N 条流的末尾：等待量约 `N × 64 KiB`，随就绪流数量线性增长。
2. 刚醒来的交互流和一直有积压的大流量流在队列里没有区别，新就绪的流排在队尾。
3. 持有节点往入口节点写下行（`internodeConn.writer`）是单一的先进先出队列，一条转发流的大积压会挡住同一条链路上所有别的转发流与控制帧。

## 2. 方案

调度只决定「已经扣过信用的帧」的出帧顺序，**线上协议一点不变**（帧、窗口、能力协商都不动），所以与已发布的 core 互通：对端看到的只是帧的交错方式变了，流内顺序与信用语义与以前相同。

三条规则，实现在 `go/internal/tunnel/sched.go` 的 `Sched`（隧道与节点间连接共用）：

- **控制帧先行**：每批先写全部控制帧（WINDOW、PING / PONG、RST、OPEN）。
- **稀疏流优先**：一条流从空闲转为就绪、排着的字节不多（不超过 `SparseMax` = 16 KiB），且上一批已经开始之后才就绪，就进 `fresh` 队列，先于持续有积压的老流出一帧；出完一帧还有数据就转入老流轮转。不需要知道流的类别：中继看到的 e2e 通道都是密文，类别没法也不该由中继判断。这是公平队列里「稀疏流优先」的做法；抢在批与批之间反复补数据的流进不了 `fresh`，换不到额外优先；`fresh` 里的流每批也至多一帧。
- **字节预算分批**：一批至多 `WriteBudget` = 128 KiB（两个最大块）的 DATA，每批至少有一条老流出一帧（稀疏流再多也饿不死老流，老流之间仍按轮转）；没轮到的留在队首，下一批先出。

每流信用上限沿用协议：每流 256 KiB、隧道 8 MiB，不改。

### 延迟上界

新到的控制帧或稀疏流的帧，在它入队之后、它的帧之前写出的 DATA 字节分两种情况：

- 同时就绪的稀疏流不多（`fresh` 队列里排在它前面的字节不超过预算）：不超过 `WriteBudget + 一块 + 传输层已接收未发出的字节`，约 192 KiB 加内核发送缓冲，**与大流量流的数量无关**。改前这个量是 `2 × N` 块（N 是就绪流数）。
- 大量稀疏流同时就绪：稀疏流之间仍按先来先出，一批至多写 `WriteBudget`（并且每批留一帧给老流），所以后来的稀疏流要等排在它前面的 `fresh` 队列里的字节写完，上界是「排在它前面的 `fresh` 队列字节 + 一块 + 内核缓冲」。这仍与大流量流无关，但随同时就绪的稀疏流数量增长；每条稀疏流排着不超过 16 KiB，所以最坏是 `稀疏流数 × 16 KiB`。

内核发送缓冲不在调度器控制下（Go 的 `Send` 在字节进内核后才返回），那一段由 TCP 本身决定。

### 为什么不是别的方案

- 优先级 / 小窗口（#57 的方案 B）要流类别，得由 core 在 OPEN 里声明，等于多暴露一项流量元数据，且小窗口伤吞吐。稀疏流优先不需要类别，效果覆盖交互流。
- 缩小隧道窗口（方案 C）对单条大流量流没有作用（先被 256 KiB 的流窗口封顶），保留为之后的旋钮，不在本 PR。

## 4. 怎么测

- `go/internal/tunnel/fairness_test.go`：限速的假传输上跑 4 / 16 / 64 条大流量流，交互流探测帧前写出的字节不超过 `WriteBudget + 3 块`（改前 4 条流就是 8 块），PONG 同样；大流量流之间份额相同、稀疏流再多也饿不死老流；流内 DATA 有序、END 在最后一块之后。度量用「入队之后写出了多少字节」，不依赖时钟，慢机器上也稳定。
- `go/internal/tunnel/sched_test.go`：调度器本身（轮转、稀疏流先出、预算、每批至少一条老流出帧、重置）。
- `go/internal/saas/internode_flow_test.go` 的 `TestInternodeWriterIsFairAcrossStreams`：持有节点写端的同一组性质。
- 基准 `go test ./internal/tunnel -run '^$' -bench 'ProbeLatency|BulkThroughput'`：限速 200 MB/s 的链路上，一条每 5 毫秒写 1 KiB 的探测流，同隧道上 0 / 4 / 32 条持续满速的大流量流，输出探测帧出帧延迟的 p50 / p99。

2026-10-24，Apple M1 Max，主机负载很高（load average 40–90，毫秒级的数字有噪声），`-benchtime 150x`，两次的范围：

| 大流量流数 | 改前 p50 / p99 (ms) | 改后 p50 / p99 (ms) |
| ---------: | ------------------: | ------------------: |
|          0 |     0.05–0.12 / 4–5 |   0.04–0.07 / 0.8–4 |
|          4 |     3.1–3.9 / 17–29 |      0.4–1.6 / 4–27 |
|         32 |      32–36 / 82–144 |    0.6–0.8 / 31–112 |

p50 的趋势清楚（改前随流数线性增长，每多一条流约多 1 ms，即一块的写出时间；改后与流数无关）；p99 在这台高负载主机上被调度抖动淹没，要在独占的 2 vCPU Linux 虚机上复测（#57 的验收口径：同源探测 p50 比别的源最多多 10 ms、p99 不超过 1.5 倍；大流量吞吐下降不超过 5%；每 GB 的 CPU 秒不超过 +5%）。吞吐与 CPU 没在本机测准：调度不多拷贝一次字节，每帧多做 O(1) 的队列操作，待维护者在虚机上跑 `BenchmarkBulkThroughput` 与 `relay-go-vs-node-bench` 的 `-probe-same` 对照。

## 5. 与 Workers 中继（`packages/relay-kernel`、`relay-runtime-workers`）

Workers 中继仍是写端先进先出：`StreamCore.pump` 把一块分成不超过 64 KiB 的帧、在信用允许的范围内一口气全部 `sendFrame`（一条流一次最多 256 KiB），没有跨流的调度；Workers 的 WebSocket 没有 `bufferedAmount`，发送立即返回，积压在 Cloudflare 边缘。按 `AGENTS.md`，Workers 版冻结功能、只修缺陷，这个问题是长期存在的性能特性而非缺陷，所以本 PR 不动它。若以后要做：在 `relay-kernel` 的 `Tunnel` 里加同样的 `Sched`（纯数据结构，可直接照 `sched.go` 移植），`pump` 改为入每流队列、由 `Tunnel` 在每个 JS 回合按预算刷出，休眠判断把队列算进去。

## 6. core 侧（AMA-Link/Armadra）要跟进的改动

core 是流的另一端，它往中继写的方向（客户端回显、终端输出、文件下载，即「源 → 客户端」）才是实测里最重的方向，中继侧再公平也救不了 core 自己的先进先出。`apps/desktop/src/core/relay/streams.ts` 与 `client.ts` 的 `send` 用同一套写法，需要同样的改动，线上协议不变：

1. 把「每流一块、直接 `ws.send`」改为「每流一个出队列（DATA / END）+ 一个控制帧队列 + 调度器」。
2. 调度器规则同 §2：控制帧先行；稀疏流（排着不超过 16 KiB、上一批开始之后才就绪）先于老流；老流每流每批一帧；一批至多 128 KiB（至少一帧）。批次号、`fresh` / `old` 两个数组、批尾把没轮到的老流留在队首，可以照 `sched.go` 逐段移植。
3. 批与批之间让出：Node 的 `ws.send` 是异步缓冲，要用 `ws.bufferedAmount`（低水位，例如不超过一个预算）决定能不能取下一批，否则调度只是把 JS 队列换成了 `ws` 的内部缓冲，延迟上界不成立；也可以用 `send` 的回调推进。
4. 流内保持顺序，END 在最后一块之后；RST 走控制队列，同时丢弃该流排着的 DATA（信用照旧归还）；流销毁、隧道关闭时清空队列。
5. 测试：同 §4 的一组，换成假 `ws`（可控的 `bufferedAmount`）：两条流一大一小，小写入在「水位 + 一块」字节以内发出；流内有序；控制帧不被 DATA 挡住；RST 与流控违规语义不变。
6. 压测程序 `loadgen` 扮演的源（`s.out`）自己是先进先出的写端，回显方向测的是它而不是 core，要么给它加同样的开关，要么用真 core 测。

另：e2e 通道内部的复用（`apps/desktop/src/core/e2e/channel.ts`、`packages/shared/src/e2e/mux.ts`）在一条外层流里也是先进先出，同一个客户端的终端与文件传输在内层会互相挡，这是 #57 评论里已经划出去的另一个 Issue，不在本设计内。
