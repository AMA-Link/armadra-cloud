# 线上中继 Workers 版切 Go 的评估报告（骨架）

状态：骨架（#161）。对比维度、测量方法、表格与决策准则先定下来，数字等 0.12 内测的实测填写；表里的「待测」不得用估算替代。

## 1. 要回答的问题

线上 `relay.armadra.com` 现在是 Cloudflare Workers 版的个人中转（`relay-runtime-workers`，`SourceDO` / `ControlDO`），按 [Go 重写设计](go-relay-design.md) D2 冻结功能、只修缺陷。路线图约定 0.12 内测稳定后按 **p99 延迟** 与 **月成本** 两项决定是否换成 Go；吞吐与运维面作辅助判断。结论只有三种：切、不切、到 1.0 前再测一次。

对比对象：

| 记号 | 部署                                                                  | 说明                                                                             |
| ---- | --------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| W    | 现网 Workers 版（`apps/relay-workers`，实际使用的 Workers 套餐）      | 不改代码，只读它的 `/metrics` 与 Cloudflare 的用量、账单                         |
| G    | Go 个人中转 `armadra-relay personal`（`deploy/personal/compose.yml`） | 部署在内测用的 VM 上（与 SaaS 同机或单独一台，评估时写明），前面是同一类反向代理 |

SaaS 节点（`armadra-relay saas serve`）用的是同一个数据面，内测期间它的指标可以作 G 的旁证，但不直接拿来比：它前面多了准入闸与节点间转发。

## 2. 对比维度

| 维度     | 定义                                                                                                                       | 主要来源                                         |
| -------- | -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| p99 延迟 | 端到端通道里一条小消息（几十字节）从客户端经中继到源、源原样回显、回到客户端的往返时间；分「空闲」与「同一隧道有大流量时」 | 外部探针（§3.2），两边同一套代码、同一地点       |
| 握手延迟 | 源建隧道的握手耗时 p99                                                                                                     | G：`relay_handshake_seconds`；W：外部探针        |
| 吞吐     | 单条通道的持续字节率；同一隧道多条通道的合计；10 MB 双向传输的耗时                                                         | 外部探针 + 两边的字节计数                        |
| 月成本   | 一个自然月里服务同样负载的全部费用，折算成「每个在线隧道每月」与「每 GB 转发」                                             | W：Cloudflare 账单与用量；G：VM 账单、流量、工时 |
| 运维面   | 部署、升级与回滚、密钥、告警覆盖、防护、事故处置、单点与地域覆盖                                                           | §5.4 的逐项核对                                  |
| 可用性   | 外部探活的可用率；握手与连接的失败率                                                                                       | 外部探活 + 两边的计数器                          |

## 3. 测量方法

### 3.1 指标对照

两边的 `/metrics` 由同一个 Prometheus 每 30 秒抓一次，覆盖同一时间窗口。名字相同的指标口径不一定相同，以下表为准：

| 含义           | W（`ControlDO.metrics`）                                          | G（`internal/obs`）                                                                | 能否直接比较                            |
| -------------- | ----------------------------------------------------------------- | ---------------------------------------------------------------------------------- | --------------------------------------- |
| 在线隧道       | `relay_tunnels`（逐个源对象汇总）                                 | `relay_tunnels`                                                                    | 能                                      |
| 在线流         | `relay_streams`                                                   | `relay_streams`                                                                    | 能                                      |
| 客户端连接     | `relay_client_websockets`（仪表）                                 | `relay_edge_connections_total{result}`、`relay_edge_streams_total{kind}`（计数器） | 不能直接比：一边是当前值，一边是累计    |
| 转发字节       | `relay_budget_used{kind="tunnel_bytes"}`（UTC 当日累计）          | `relay_bytes_total{direction}`                                                     | 按日换算后能                            |
| 请求数         | `relay_budget_used{kind="requests"}`（当日，按 Workers 计费口径） | 无对应（VM 不按请求计费）                                                          | 只进 W 的成本                           |
| 握手耗时       | 无                                                                | `relay_handshake_seconds`                                                          | 只能用外部探针比                        |
| 心跳超时       | 无                                                                | `relay_heartbeat_miss_total`                                                       | 只看 G                                  |
| 运行时调度延迟 | 无（平台托管）                                                    | `relay_sched_latency_seconds`                                                      | 只看 G，用来判断 G 的延迟是不是机器不够 |

所以两项决定性指标（p99 与成本）都不靠两边自报的指标：p99 用 §3.2 的外部探针，成本用账单。

### 3.2 外部探针与压测脚本思路

- **角色**：探针同时扮演两端，与 `go/bench/loadgen` 的做法相同：若干「源」经 `/t/v1` 握手，把收到的端到端字节原样回显（守信用窗口）；若干「客户端」经 `/_relay/e2e` 开通道，发带发送时刻与序号的记录，统计往返时间并校验按序、不丢、不重。
- **要补的能力**：`loadgen` 现在只对本地 `armadra-relay dev --debug` 与它自签的测试令牌。对已部署的中继要加一个模式：用一个专门的评估账号（不是任何用户的账号）登记的源与签出的中继令牌，目标地址可配。这一步在评估开始前单独做，作为前置项（§6）。
- **阶段**（每个阶段至少 10 分钟，两边轮流跑、不同时压同一个出口）：
  1. 空闲：N 条隧道，不开通道，看握手耗时与心跳。
  2. 交互：每条隧道一条通道，每秒一条小消息，记往返时间。
  3. 交互 + 大流量：同一隧道上另开一条通道持续传大块数据，交互通道照常探测（看公平调度在两边的差别）。
  4. 爬坡：隧道数按 1×、2×、4× 内测峰值递增，到 p99 明显拐弯或 W 触到配额为止。
- **地点**：探针放在内测用户所在的主要地区（至少两个），每个地点对 W、G 各跑一遍；写明探针机器的规格与网络。
- **不打生产**：W 用 staging 的 Worker（同一套代码与套餐），G 用评估专用的实例；压测本身产生的 Workers 费用单独记下，不计入月成本。
- **探活**：评估期间（至少 7 天）每分钟一次的外部握手 + 单次往返，算可用率。

### 3.3 成本采集

- **W**：内测期间一个完整自然月的 Cloudflare 账单（Workers 基础费、请求、Durable Objects 的请求与 Duration、存储）；每天记一次 `relay_budget_used` 两项，用来把账单折算到负载。
- **G**：VM 的月费（与 SaaS 同机时按 CPU 与内存占用比例分摊，写明分摊方法）、出向流量费、备份存储、证书与域名（若新增）；运维工时按评估月实际记录的处置次数与时长估，单独一行，不与机器费混在一起。
- **折算**：同一个月的平均在线隧道数（`avg_over_time(relay_tunnels[30d])`）与转发总字节，算出「每隧道每月」与「每 GB」；再按 1.0 预期规模（路线图给的团队数）外推一次，外推的假设写在表下。

## 5. 决策准则

下面的阈值是建议值，评审本报告时由维护者确认后再填数据；数据出来之后不改准则。

- **切 Go**，同时满足：
  1. 所有主要地区的「交互往返」与「交互 + 大流量」两个阶段，G 的 p99 不高于 W 的 p99 的 1.1 倍；
  2. 评估月的合计成本，以及外推到 1.0 规模的月合计，G 都不高于 W；
  3. G 的外部探活可用率不低于 W；
  4. §6 的前置项都已完成（尤其是数据迁移与回滚演练的方案）。
- **不切**，满足任一：任一主要地区 G 的 p99 高于 W 的 1.2 倍；或 G 不便宜也不更快。
- **到 1.0 前再测**：其余情况（例如 G 更快但贵，或便宜但在某个地区更慢），把差距与原因写进结论，1.0 之前按同一方法再测一次。
- **W 触到硬上限**（套餐配额、单个对象的并发限制）而 G 在同一负载下正常：即使成本略高也倾向切，结论里写明触到的是哪一条限制。
- 结论为「切」时按路线图走 G4 同样的升级与回滚演练，演练通过后 Workers 版归档；结论为「不切」时 W 继续冻结、只修缺陷。

## 6. 前置项与遗留

- `loadgen` 加「对已部署中继」模式（评估账号、可配目标、结果按 §4 的表格输出）。
- 评估账号与源：专门建，评估结束后撤销；探针不碰任何用户的数据。
- W 的 `/metrics` 没有握手直方图与调度类指标，延迟只能靠外部探针，这是方法上的已知限制，不为评估改冻结的 Workers 代码。
- 个人中转的数据从 W（DO SQLite）迁到 G（SQLite，同一份迁移）的导出办法目前没有；结论为「切」之前要先有方案并演练。
