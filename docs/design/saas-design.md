## §0 摘要

- **租户是团队。**
  - 每个账号自带一个**个人空间**，也可以创建或加入多个**团队**。
  - 主机、授予、分享链接、配额、计费、审计都挂在空间上：个人空间或某个团队。
  - 团队里可以建**分组**，按分组授予主机访问。
  - 以后要企业版，就在团队之上加「组织」，把多个团队收到一个计费与单点登录边界下（§1.4）。现在不做。
- **云端只管「谁能以什么角色到达哪台主机」。**
  - 断言把意图带进 core：团队、角色、范围。最终判定仍在 core。
  - 中继只按令牌放行与计量，看不到任何内容。
- **能力分十二组（§3）**：账号与身份、团队、分组、主机、授予与访问申请、分享、中继与连接、通知、审计、用量与计费、API 与集成、运营后台。
- **分三期（§9）**：
  - M1 先让「团队一起用几台主机」跑通；
  - M2 补齐安全与计费；
  - M3 是企业能力。

## §1 租户模型

### 1.1 实体

```text
账号 account                     登录主体；邮箱唯一；可以有多种凭据（口令、passkey、OAuth、SSO）
 ├ 个人空间 personal space        每个账号一个，不可删除；只有本人
 └ 团队成员身份 membership         账号在某个团队里的角色
团队 team                        租户：成员、分组、主机、授予、链接、配额、计费、审计、设置的边界
 ├ 成员 member                   owner / admin / member / billing；外部协作者 guest
 ├ 分组 group                    团队内的一组成员（部门、项目组），授予的主体之一；组长 lead
 ├ 主机 host（= 源 source）       一台 core（桌面 / 服务器壳 / 托管），属于且只属于一个空间
 │  └ 工作空间 workspace          core 内；授予与分享的最小单位
 │     └ 会话 session            终端 / ACP 会话；只做只读分享的范围
 ├ 邀请 invitation / 链接 link
 └ 计划与订阅 plan / subscription
设备 device                      账号的登录设备（浏览器、桌面、手机、CLI）
```

### 1.2 主机属于空间

- **归属**：登记主机时选空间。注册令牌由某个空间签发，主机就归那个空间；这台主机的 owner 是登记它的账号。
  - 个人空间的主机只有本人可达，再加上本人发出的分享。
  - 团队的主机按授予可达（§3.5）。
- **转移**：
  - 个人 → 团队：主机 owner 发起，团队 admin 接受。
  - 团队 → 团队：两边的 admin 都确认。
  - 转移后，原空间签过的断言与链接全部作废。
- **成员离开**：主机留在团队里，owner 改成团队 owner。core 侧对应的本地 owner 不变，是那台机器自己的账号。云端只是不再给离开的人签断言。

### 1.3 两层真相（沿用）

| 层   | 存哪里              | 管什么                                                                                            | 不管什么                 |
| ---- | ------------------- | ------------------------------------------------------------------------------------------------- | ------------------------ |
| 云端 | PostgreSQL          | 账号、团队、分组、主机目录、授予、链接与邀请、配额与计费、云端审计                                | 任何画布、终端、文件内容 |
| core | SQLite `identity_*` | 主体、授予（`identity_grants`，`origin = cloud:<iss>` 的那部分随断言同步）、设备、会话、core 审计 | 云账号口令               |

### 1.4 以后加组织（企业版）

- **组织在团队之上**：一个组织拥有多个团队，统一单点登录、SCIM、计费与审计导出。
- **数据模型**：`teams.organization_id` 可空，现在就留这一列。
- **断言**：`org` 声明保留给它；团队用 `team` 声明（§6）。
- **对现有团队的影响**：现有团队不受影响，可以被「认领」进组织。

## §2 角色与权限

### 2.1 团队角色

| 能做                                    | owner | admin |     member      | billing  |      guest       |
| --------------------------------------- | :---: | :---: | :-------------: | :------: | :--------------: |
| 看团队目录（成员、分组、主机列表）      |   ✓   |   ✓   |        ✓        | 成员列表 | 只看被授予的主机 |
| 邀请 / 移除成员、改角色（不能动 owner） |   ✓   |   ✓   |        —        |    —     |        —         |
| 转移 owner、删除团队                    |   ✓   |   —   |        —        |    —     |        —         |
| 建 / 改 / 删分组，指定组长              |   ✓   |   ✓   |        —        |    —     |        —         |
| 组长增删本组成员                        |   ✓   |   ✓   |    组长可以     |    —     |        —         |
| 登记主机到团队                          |   ✓   |   ✓   | 设置允许时可以  |    —     |        —         |
| 授予 / 撤销主机访问                     |   ✓   |   ✓   | 主机 owner 可以 |    —     |        —         |
| 签主机分享链接                          |   ✓   |   ✓   |   按主机设置    |    —     |        —         |
| 处理访问申请                            |   ✓   |   ✓   | 主机 owner 可以 |    —     |        —         |
| 看团队审计                              |   ✓   |   ✓   |        —        |    —     |        —         |
| 改计划、看账单、付款方式                |   ✓   |   —   |        —        |    ✓     |        —         |
| 团队设置（安全策略、域名、缺省角色）    |   ✓   |   ✓   |        —        |    —     |        —         |
| 建团队 API 令牌                         |   ✓   |   ✓   |        —        |    —     |        —         |

- **guest**（外部协作者）：
  - 不占计费席位，按计划另算数量；
  - 只能看到被直接授予的主机；
  - 不能被加进分组；
  - 团队可以在设置里关掉 guest。
- **每个团队至少一个 owner**：最后一个 owner 不能离开或降级，要先转移。

### 2.2 主机角色（沿用 core 四档 + 会话只读）

| 角色             | 能做（core 判定）              |
| ---------------- | ------------------------------ |
| `viewer`         | 只读：画布、终端输出、事件     |
| `editor`         | 编辑画布、文件                 |
| `operator`       | 再加启动 / 停止 Agent 与终端   |
| `driver`         | 再加驱动他人的 Agent、回答审批 |
| `session-viewer` | 单个会话的只读焦点页           |

授予的范围是整台主机，或一组工作空间（`ws:<id>` 列表）；会话只读走 `sess:<id>`。

## §3 能力清单

每条标出期别（M1 / M2 / M3）。

### 3.1 账号与身份

| 能力                               | 期  | 要点                                                                                        |
| ---------------------------------- | :-: | ------------------------------------------------------------------------------------------- |
| 邮箱 + 口令注册                    | M1  | 口令策略与个人中转相同（scrypt、四条规则）；注册后发验证邮件                                |
| 邮箱验证                           | M1  | 未验证可以登录，但不能登记主机、签链接、被授予（防垃圾）                                    |
| 登录、刷新、登出                   | M1  | 与个人中转相同；Web 用 `__Host-armadra-cloud` Cookie + `X-Armadra-CSRF`，原生端用 Bearer    |
| 找回口令                           | M1  | 邮件一次性链接，30 分钟；完成后撤销全部设备                                                 |
| 设备码登录                         | M1  | 给桌面 core 与 CLI 用：`auth.deviceStart` / `devicePoll` / `deviceApprove`，8 位码，10 分钟 |
| 设备与会话管理                     | M1  | 列表、最近使用、撤销单台或全部                                                              |
| 改邮箱、改口令、改显示名与头像     | M1  | 改邮箱要验证新地址，并通知旧地址                                                            |
| 两步验证（TOTP + 恢复码）          | M2  | 团队可强制要求                                                                              |
| passkey                            | M2  | 登录与两步验证都可以用                                                                      |
| GitHub / Google 登录               | M2  | 绑定到已有账号要先验证邮箱                                                                  |
| 注销账号与导出数据                 | M2  | 先转移名下团队的 owner；7 天冷静期；导出账号、设备、授予、审计                              |
| 团队单点登录（SAML / OIDC）与 SCIM | M3  | 按验证过的域名                                                                              |

### 3.2 团队

| 能力                       |   期    | 要点                                                                                                                     |
| -------------------------- | :-----: | ------------------------------------------------------------------------------------------------------------------------ |
| 创建团队                   |   M1    | 名称、slug（URL 用，唯一）、头像；创建者是 owner；新团队用 Free 计划                                                     |
| 邀请成员                   |   M1    | 按邮箱定向邀请，指定角色；7 天有效；可撤销；接受时要登录且邮箱一致                                                       |
| 邀请链接                   |   M2    | 团队级加入链接，可限邮箱域名、次数、有效期                                                                               |
| 按域名自动加入             |   M3    | 验证过的域名下的新账号自动成为 member，或进入待审批                                                                      |
| 改角色、移除成员、自己离开 |   M1    | 移除时撤销此人的全部团队授予，踢掉在线连接（§3.5）                                                                       |
| 转移 owner                 |   M1    | 目标必须是 admin                                                                                                         |
| 删除团队                   |   M1    | 先撤销全部主机，或把主机转走；30 天内可恢复，之后清除                                                                    |
| 团队设置                   | M1 / M2 | M1：成员能否登记主机、缺省主机角色、是否允许 guest、是否允许匿名分享链接。M2：强制两步验证、会话时长上限、允许的邮箱域名 |
| 切换空间                   |   M1    | 只在控制台顶部：个人 / 各团队，记住上次选择。客户端不做手动切换，见 §8                                                   |

### 3.3 分组

| 能力                 | 期  | 要点                                                   |
| -------------------- | :-: | ------------------------------------------------------ |
| 建 / 改名 / 删除分组 | M2  | 删除分组即撤销以它为主体的授予                         |
| 增删组员、组长       | M2  | 组长可以管理本组成员；组员必须是团队成员（不含 guest） |
| 按分组授予主机       | M2  | 组员的有效角色取所有来源里最高的那个                   |

M1 用「团队全员」与「单个成员」两种授予主体就够了。分组放 M2，数据模型 M1 就建好。

### 3.4 主机

| 能力                        | 期  | 要点                                                                         |
| --------------------------- | :-: | ---------------------------------------------------------------------------- |
| 登记主机到空间              | M1  | 注册令牌带空间；设备码登录后，core 可以直接列出能登记的空间供选择            |
| 主机目录                    | M1  | 在线状态、core 版本、最后在线、所属空间、owner、标签；随 me-stream 实时更新  |
| 改名、标签                  | M1  | 标签只用于筛选与成组授予（M2）                                               |
| 主机设置                    | M1  | 谁能签分享链接（owner / admin / 有 driver 角色的人）、是否允许访客、缺省角色 |
| 撤销主机                    | M1  | 关隧道、断开所有客户端、作废断言与链接                                       |
| 转移空间                    | M2  | 见 §1.2                                                                      |
| 主机组（按标签授予）        | M2  | 对一个标签授予，等于对所有带这个标签的主机授予，新加的主机自动生效           |
| 托管主机（云端代跑的 core） | M3  | 按计划计费；先只做设计预留                                                   |

### 3.5 授予与访问申请

| 能力       | 期  | 要点                                                                                                                 |
| ---------- | :-: | -------------------------------------------------------------------------------------------------------------------- |
| 授予       | M1  | 主体：团队全员、成员（含 guest）、分组（M2）。角色四档。范围：整台或工作空间列表。可设到期                           |
| 有效权限   | M1  | 同一个人从多条授予里取最高角色、范围取并集；断言只带结果                                                             |
| 撤销即生效 | M1  | 写撤销表（`jti`）并发 `relay:ctl kick`；下次 `cloud/login` 时 core 清掉该主体的云端授予；core 侧授予有 30 天租约兜底 |
| 访问申请   | M2  | 成员对看得到但不可达的主机点「申请访问」，选角色与理由；主机 owner 或 admin 批准或拒绝，邮件与站内都通知             |
| 访问清单   | M1  | 每台主机「谁能访问、从哪条授予来、何时到期」；可以导出                                                               |
| 定期复核   | M3  | 每季度提醒 admin 复核，没确认的授予到期失效                                                                          |

### 3.6 分享

| 能力                         | 期  | 要点                                                                         |
| ---------------------------- | :-: | ---------------------------------------------------------------------------- |
| 主机 / 工作区 / 会话分享链接 | M1  | 现有 `links.*` 加空间维度；SaaS 缺省要求登录云账号，团队设置可以允许匿名访客 |
| 定向邀请到主机               | M1  | 按邮箱邀请到某台主机（或工作区），对方接受后成为该主机的 guest 授予          |
| 链接管理                     | M1  | 列表、备注、用量、到期、撤销（连同已进来的人）                               |
| 只读会话直播                 | M1  | `sess:<id>` + 只读，复用已有能力                                             |

### 3.7 中继与连接

| 能力             | 期  | 要点                                                                                 |
| ---------------- | :-: | ------------------------------------------------------------------------------------ |
| 多节点中继       | M1  | Go 中继节点、共享路由、节点间转发（Go 重写 G5）                                      |
| 断言与中继令牌   | M1  | 断言带 `team`、`role`、`scp`；中继令牌带 `team`，供限流与计量                        |
| 按团队限流与计量 | M1  | `edge.concurrent.team`、`edge.connect.team`；流量按团队 × 主机 × 成员 × 设备记小时桶 |
| 连接状态事件     | M1  | me-stream：主机上下线、被撤销、成员与授予变化、链接被用                              |
| 区域             | M3  | 多区域节点；团队可以选首选区域，数据驻留只涉及控制面元数据                           |

### 3.8 通知

| 能力         | 期  | 要点                                                                           |
| ------------ | :-: | ------------------------------------------------------------------------------ |
| 事务邮件     | M1  | 验证、找回口令、团队邀请、主机邀请、新设备登录提醒；中英双语模板，按账号语言发 |
| 站内事件     | M1  | 经 me-stream 推到客户端（访问申请、授予变化、邀请）                            |
| 通知偏好     | M2  | 按类别开关邮件；安全类邮件不能关                                               |
| 团队 Webhook | M3  | 主机上下线、成员变动、授予变动；签名与重试                                     |

### 3.9 审计

| 能力         | 期  | 要点                                                                                                                       |
| ------------ | :-: | -------------------------------------------------------------------------------------------------------------------------- |
| 团队审计日志 | M1  | 记录这些事件：成员、分组、主机登记与撤销、授予、链接、设置、计划变更，以及每一次断言签发（按 `jti`，可以与 core 审计对账） |
| 账号安全日志 | M1  | 登录、新设备、改口令、两步验证变化，本人可见                                                                               |
| 查询与导出   | M2  | 按人、按主机、按时间筛选；CSV / JSON 导出                                                                                  |
| 保留期       | M2  | 按计划：Free 7 天、Pro 30 天、Team 90 天、Enterprise 1 年起                                                                |

审计不记任何内容与令牌，只记主体、动作、对象、时间、来源 IP 的前缀。

### 3.12 运营后台（只给运营方）

| 能力         | 期  | 要点                                                 |
| ------------ | :-: | ---------------------------------------------------- |
| 查账号与团队 | M1  | 只读：计划、用量、主机数、状态；看不到任何内容与令牌 |
| 停用与恢复   | M1  | 停用账号或团队：拒绝登录与断言、踢掉连接；写审计     |
| 中继节点     | M1  | 节点列表、在线隧道数、排空（GOAWAY rebalance）       |
| 滥用处理     | M2  | 按流量异常与举报处理；冻结链接                       |
| 功能开关     | M2  | 按团队灰度                                           |
| 服务状态页   | M2  | 对外的状态页                                         |

后台不提供「以用户身份登录」；排障只看元数据。

## §4 安全要求（贯穿各期）

- **防暴力破解与人机验证**：登录、注册、找回口令、链接接受都按 IP 与账号限流；Turnstile 可选。
- **令牌**：寿命与撤销规则与个人中转相同；断言按 `jti` 进审计。
- **静态加密**：签名私钥与第三方凭据用主密钥（`ARMADRA_CLOUD_MASTER_KEY`）包裹；数据库连接只用 TLS。
- **查询隔离**：所有查询都带空间过滤（`team_id` 或 `account_id`），由存储层统一加，测试覆盖「跨团队读不到」。
- **团队删除与账号注销**：先撤销访问，再进冷静期，最后清除；清除任务进作业队列。
- **事故开关**：一键停签断言、停注册（运营后台）；中继侧拒绝新连接、保留在线连接。

## §6 断言、令牌与协议的变化（协议 1.4）

- **断言声明**：
  - `team { teamId, role: owner|admin|member|billing|guest }`：所属团队与团队角色。主机属于个人空间时不带。

## §8 客户端与控制台（Armadra）

- **客户端侧栏不改结构**，沿用已经上线的远程访问重设计（Armadra `docs/design/remote-access-redesign.md`，契约 §68）：
  - 侧栏三组：「这台电脑 / 我的其他电脑 / 共享给我的」。
  - 当前源由打开的工作空间推出来，没有手动「切换服务」。
  - SaaS 带来的主机按归属落进这三组：自己登记的进「我的其他电脑」，经团队授予或分享来的进「共享给我的」，并按团队名分小组。
  - 界面上不出现「源 / 中继节点 / 签发方 / 断言」这些词。
- **控制台**：
  - 做进 Armadra `apps/web`，作为「云端」分区，与个人中转托管的页面共用一套设计系统与 i18n。
  - 只用现有 shadcn 组件。
  - 由 `app.armadra.com` 托管。
  - 空间切换只在控制台。
- **浏览器里的凭据模型**（合并自 Armadra `docs/design/platform/client-packages.md` §7，新增 `browser-cloud` 凭据提供方）：
  - 控制台本身用 `__Host-armadra-cloud` Cookie。
  - 到各主机的中继令牌与断言只放内存。
  - 刷新令牌不进 localStorage。
  - 页面 CSP 由控制面下发。
- **新建连接**：「SaaS」走设备码登录（§11.5），深链 `armadra://cloud`。实现清单沿用 `multi-tenant-saas-design.md` §6.3 的 A7-5：
  - `assertionFor` 的 saas 分支；
  - `remoteAdd { kind: "saas" }` + `remoteDevicePoll`（契约 §33 预留的两个）；
  - 远程访问页与手机「添加连接」的 SaaS 入口。
- **主机登记**：core 的「远程访问」页登录 SaaS 后选空间再登记。团队设置不允许 member 登记时，这一项灰掉，并显示原因码对应的文案。
- **分享对话框**：在现有的「链接」之外，加「团队成员 / 分组」（授予）与「按邮箱邀请」（主机邀请）。缺省只读、7 天。
- **新设备待信任**：主机 owner 与团队 admin 在客户端与控制台都能看到，并直接处理（§11.4）。
- **团队管理页**（控制台）：成员、分组、主机、授予、链接、审计、用量与计划、设置。
- **手机**：只做查看，以及处理访问申请、邀请与新设备信任；管理类页面引导到网页。

## §11 合并自旧方案的细节（规范）

以下各条来自以前的方案，仍然有效，实现以本节为准。

### 11.1 一源多路与身份合并

来源：`multi-tenant-saas-design.md` §2.1 #6、#15、§2.3；Armadra 契约 §55。

- SaaS 只是 core 的又一条「远程服务」（`remote_services.kind = saas`），可以和局域网、公网个人中转同时登记，一源多路，凭据各占一槽。
- SaaS 的 `sub` 是账号 uuid，issuer 只有一个。同一个人经多条路连到同一台主机，在 core 里是同一个主体。

### 11.2 授予同步

来源：`multi-tenant-saas-design.md` §3.3(a)、§3.4；Armadra 契约 §60；远程访问重设计 §2。

- **准入**：断言带 `team` + `role` 时，`cloud/login` 不要邀请令牌，按 `role` 建成员（§6）。
- **整份替换**：每次登录，把该主体 `origin = cloud:<iss>` 的授予整份替换成断言里的。本地 owner 手工给的授予（`origin = ''`）不动。
- **租约**：授予带 `expires_at_ms`，取 min（断言租约 30 天，每次登录续；邀请到期）。即使此人改走局域网直连，租约到期授予也失效。
- **撤销走两道门**：
  1. 云端写撤销（`jti`）并 `kick`，中继拒门；
  2. 下次登录时 core 清掉该主体的云端授予，或按租约到期。
- **判定在 core**：云端只合成意图，core 是最终判定点，这一原则不变。

### 11.3 分享语义

来源：`multi-tenant-saas-design.md` §3.3(b)；Armadra `platform-saas-architecture.md` §6.2；`platform/cloud-control-plane.md` §5.4；Armadra 契约 §80。

- **两种到达方式，一个终点**：链接（匿名接受 + `#secret`）与邀请（定向、要登录）在 core 都落成一张邀请，所以 core 的接受与消费逻辑不变。
- **用量以 core 为准**：core 是用量的真相；云端的 `max_uses` 只做提前拒绝。
- **接受事务**：条件更新加一。并发测试：10 个同时接受、`max_uses = 5`，恰好 5 个成功；重复接受是幂等的。
- **会话分享永远只读**：向他人终端写入等于替 Agent 回答权限提示，可写只在工作区级（editor 以上），写终端要 driver。
- **撤销链接**：连同已经进来的人一起停用，即 `guest:<linkId>:` 前缀的主体。
- **链接自带信任信息**：链接片段带源身份指纹，并有 `max_devices` 限制（契约 §80）。

### 11.4 端到端下的新设备信任（新决定，Q9）

**现状**：断言只是「引荐」。core 要拿到会话，还要求设备公钥在 `trusted_devices` 里（Armadra 契约 §77、§80；工作区 `docs/armadra/plans/relay-e2e-and-traffic-stats.md` §4.8–§4.10）。受信的途径有四种：

- 扫码；
- 已受信设备背书；
- 本机 SAS 确认；
- 分享链接（`link:<linkId>`）。

**问题**：团队成员第一次从新设备连团队主机，会停在 `device_pending`，要有人在那台机器上核对验证码，团队用起来卡住。

**决定**：

- **云端不担保设备**。否则控制面运营方就能冒充设备，等于放弃端到端。
- **背书的人**：由主机 owner 或团队 admin 从**自己已受信的设备**背书。
  - 待信任请求经云端事件推给这些人（控制台、客户端、手机都显示），带设备名与平台；6 位校验码由新设备显示，不经云端，背书人在自己已受信的设备上输入（cloud-api §31）。
  - 批准动作经端到端通道发到主机，用的是现有的「已受信设备背书」路径（契约 §77）。云端只转发通知，看不到也改不了背书内容。
- **团队设置**「新设备背书人」：
  - 主机 owner；
  - 主机 owner + 团队 admin（缺省）；
  - 加上成员本人从自己另一台已受信设备背书（这一项缺省开）。
- 走分享链接进来的访客，仍按链接的 `max_devices` 与指纹钉扎，不变。

### 11.5 设备码

来源：`platform/cloud-control-plane.md` §5.2；`platform-saas-architecture.md` §5.4。

- **状态**：`pending → approved → consumed`，或 `denied` / `expired`，10 分钟过期。
- **用户码**：8 位，字母表 `BCDFGHJKLMNPQRSTVWXZ`，去掉了容易混淆的字符。
- **核验页**：`verificationUrl = https://app.armadra.com/device?code=<userCode>`。
- **轮询**：间隔 5 秒，太快答 `rate_limited`。
- **批准**：要已登录的浏览器会话，页面显示发起设备的平台与名字。

### 11.6 Cookie、CSRF 与来源

来源：`cloud-api` §1；`platform/cloud-control-plane.md` §5.1；`multi-tenant-saas-design.md` §5.7。

- **单一来源**：issuer = `APP_ORIGIN`，`__Host-armadra-cloud` Cookie 只用于控制台自己的来源。
- **两种凭据不混用**：其他调用方（core、原生 App、跨源页面）一律 Bearer；同一个请求带了两种就拒绝。
- **写操作校验**：每个写操作都校验 `X-Armadra-CSRF`，`Origin` 头必须恰好出现一次。
- **CSP**：托管页面的 CSP 要覆盖 `*.src.armadra.com` 的连接。

### 11.7 已签令牌的即时撤销

来源：`platform/cloud-control-plane.md` §4、§5.3。

- **签发索引**：签发时把 `jti` 记进 Redis 集合 `issued:acct:<id>` 与 `issued:src:<id>`，TTL 1 小时，与令牌最长寿命相同。
- **撤销**：撤销账号、设备、主机或授予时，按集合整批写撤销表并广播。
- **断言限流**：`assert.acct` 每账号每分钟 60 次。
- **撤销主机**：`kick` + 撤销已签令牌 + 发 `sourceRevoked`。

### 11.8 账号与配置细节

来源：`platform/cloud-control-plane.md` §3.1、§7、§9。

- **表结构**：
  - `credentials` 之外，另有 `account_lockouts`（与个人中转同一套锁定规则）；
  - `account_sessions.rotation`（刷新旋转计数）；
  - `device_codes` 与 `email_tokens` 的列按该文档 §3.1。
- **常用口令表**：与个人中转、core 三方一致，测试按 sha256 比对；HIBP 查询可选（`HIBP_URL`）。
- **访问日志**：字段走白名单。
- **环境变量**：`ARMADRA_CLOUD_ISSUER`、`APP_ORIGIN`（M1 两者相同）、`DATABASE_URL`、`REDIS_URL`、`MASTER_KEY`、`RELAY_DOMAIN`、`REQUIRE_EMAIL_VERIFIED`、`OAUTH_<ID>_*`、`HIBP_URL`、`WEB_ROOT`、`SMTP_*`、`LOG_LEVEL`。

### 11.9 主机侧安全

来源：`platform-saas-architecture.md` §10.1、§11.4；Armadra `platform/core-packages.md` §8。

- **团队主机就是共享机器**：能进主机终端的成员，就能以那台 core 的系统用户身份开 shell。控制台的「登记到团队」处要明确提示这一点。建议一个团队一台 core，或者放进容器 / 独立系统用户（`install --run-as`）。
- **core 侧上限**：`limits.terminalsPerPrincipal`（缺省 16）与 `limits.agentsPerWorkspace`（缺省 8），防一个成员占满主机。这是 Armadra 侧的工作，随 M1 的 Armadra PR 一起做。

### 11.10 托管主机（M3）的约束

来源：`platform-saas-architecture.md` §2.2、§2.3、§10.2。

- 在共享基础设施上替用户跑 CLI 的订阅登录，有条款风险。托管主机只提供运行环境，CLI 登录由用户自己完成（D12）。
- 每个租户一个卷，注册令牌注入；资源按 cgroup 限制。

### 11.11 推送中继

来源：`platform-saas-architecture.md` §1.3、§3.2；Armadra `external-services.md` W-PUSH。

- Armadra 的 `apps/push-relay`（只转端到端加密信封、无状态）作为 SaaS 部署的一部分，和控制面放在同一个 compose 里（Go 重写 §3.10）。
- App 证明（安全审查 L5）随商店账号就绪后补。

### 11.12 兼容窗口

来源：`platform-saas-architecture.md` D19。

- 控制面与中继同时支持协议的当前 major 与上一个 major，至少 12 个月。
- 协议 1.x 内只做加法。

### 11.13 中继与控制面能看到什么

来源：工作区 `relay-e2e-and-traffic-stats.md` §5；`relay-e2e-only.md`。

- 端到端保护的是内容，不是元数据。中继与控制面看得到：谁、何时、连哪台主机、多少字节。
- 由中继或控制台托管的网页，运营方可以在下发时篡改。控制台和控制面属于同一方，所以控制台不提供额外保护。
- 高敏感场景用桌面客户端或原生 App。

### 11.14 计量扩展

来源：`relay-e2e-and-traffic-stats.md` D4。

- 流量桶多一个维度 `team`。
- 按团队按字节计费的口径是 `edge.e2e.bytes`：只在入口节点计（Go 重写 §3.6）。
